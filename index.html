문제

담당 역할

런타임의 역할 분리

반복 호출과 실패 비용 줄이기

설계와 구현 자세히 보기＋

문제

Reddit Translator는 수집·번역·요약을 도구로 묶었지만, 어떤 글을 다룰지 고르고 발행 여부를 정하는 판단과 실행 시점은 여전히 사람이 버튼을 눌러야 했습니다. 이 반복되는 판단을 사람의 개입을 최소화한 상태로 자동화하는 것이 목표였습니다.

담당 역할

수집·계획·작성·검토·판정·승인·발행으로 이어지는 7단계 무인 루프를 LangGraph로 단독 설계·개발했습니다. 로컬 모델 구성, 코드 게이트, 상태 체크포인트, Discord 승인 흐름, 운영 대시보드까지 담당했습니다.

LangGraph로 짠 상태 기반 루프

LangGraph의 StateGraph로 7개 노드(collect, plan, execute, gate, judge, approve, publish)를 정의했습니다. 초심자를 위해 풀어 쓰면, LangGraph는 각 단계를 노드로 놓고 하나의 상태(state) 객체를 노드에서 노드로 넘기며 순서와 분기를 관리하는 도구입니다. 상태는 OrchestratorState라는 타입 정의로, 수집한 글·계획·초안·게이트 결과·판정 결과·승인·발행 정보를 담습니다. 여기에 steps 필드는 operator.add 리듀서를 써서 각 노드가 남긴 기록(단계·모델·백엔드·토큰·지연·판정)을 자동으로 이어 붙여 근거 기록으로 쌓습니다. 조건부 엣지로 수집 이후, 게이트 이후, 승인 이후의 진행 방향을 상태 값에 따라 나눕니다.

역할로 나눈 로컬 모델

16GB 통합 메모리라는 제약 아래, 큰 모델 하나 대신 역할별 작은 모델 세 종으로 나눴습니다. 라우터·계획·추출은 lfm2.5:8b(MoE, 활성 약 1.5B), 초안·판정 같은 품질 작업은 qwen3.5:9b(dense), 병렬·분류 같은 가벼운 작업은 qwen3.5:4b(dense)가 맡습니다. 운영은 Ollama(GGUF), 벤치마크는 MLX로 이중 백엔드를 두고 같은 16GB 위에서 돌립니다. 워커 노드는 think=False로 두어 추론 토큰이 아니라 결과 자체를 받도록 했습니다.

코드 게이트 먼저, 판정기는 그다음

초안이 나오면 선정한 글의 존재·중복·길이·금칙어를 코드로 먼저 검사합니다. 이 게이트는 문제가 있으면 닫히도록(fail closed) 설계해, 나쁜 초안에 판정기 토큰을 쓰기 전에 걸러냅니다. 통과한 초안만 qwen3.5:9b 판정기가 정확성·비중복·가독성을 1-5점과 확신도 0-1로 평가합니다. Ollama의 format 필드로 JSON 스키마 기반 constrained decoding을 걸어 형식을 디코딩 시점에 강제합니다.

멈췄다 이어지는 승인 흐름

체크포인터로 PostgresSaver를 써서 그래프 상태를 Postgres에 저장합니다. 승인 노드에서 interrupt()를 호출하면 그래프는 그 지점에 상태를 저장한 채 멈추고, Discord 봇 버튼이나 resume CLI가 결정을 전달하면 Command(resume=...)로 멈춘 지점부터 이어집니다. 덕분에 실행 중간에 프로세스가 재시작되어도 진행 상태가 살아남습니다. --no-db 모드에서는 메모리 체크포인터를 씁니다.

근거를 남기는 운영 대시보드

Spring Boot 기반 /orchestra 대시보드(Java 21)를 붙여 같은 Postgres를 읽기 전용으로 조회합니다. 실행 목록, 단계별 지연·토큰·판정, 모델별 성공률과 판정 점수 평균을 보여주고, 각 실행을 눌러 단계별 근거로 들어갈 수 있습니다.

결과

M4 Mac mini 16GB에서 수집부터 발행까지 전체 루프가 로컬 모델로 동작하고, 구조화 출력이 강제되며 Postgres 체크포인트가 유지됩니다. 승인 단계에서 그래프가 멈춰 Discord 미리보기를 보내고, CLI와 Discord 버튼 양쪽으로 재개됩니다. 다이제스트는 블로그 저장소에 Fuwari 글로 커밋되며, main 푸시는 기본 꺼짐으로 두었습니다. 핵심 단계는 전부 로컬 실행이라 API 비용은 0원입니다.

설계에서 고려한 점

구조화 출력은 형식을 강제할 뿐 내용의 정확성까지 보장하지 않습니다. 그래서 코드 게이트로 선정 유효성·중복·길이·금칙어를 먼저 닫고, LLM 판정기로 내용 품질을 점수화하며, 마지막으로 사람이 Discord에서 승인하는 계층형 검토를 뒀습니다. 모델 크기가 아니라 역할 분리·스키마 강제·단계별 판단이 신뢰성을 만든다는 판단입니다.

문제

수집 데이터의 키워드·감정·요약 분석을 배치로 처리하면서 모델 실행 환경, 응답 형식, 중복 실행과 실패 재처리를 함께 관리해야 했습니다.

담당 역할

stateless LLM 프록시 서버와 Spring Batch 분석 파이프라인을 단독 설계·개발했습니다. 수집 엔진의 분산 처리와 운영 안정화도 담당했습니다.

모델 호출과 배치 상태 분리

내부 GPU의 Ollama와 외부 AI API를 동적으로 분기하도록 구성했습니다. 분석 유형별 시스템 프롬프트 14종을 파일로 관리하고 Ollama 호출에 JSON Schema 기반 constrained decoding을 적용했습니다.

실행 환경에 맞춘 모델 구성

Gemma 4 26B(MoE), gpt-oss 120B 등 모델을 GPU 메모리 조건에 맞춰 선정하고 양자화·Modelfile·num_ctx를 조정했습니다.

반복 실행 가능한 배치

100건 단위 청크와 병렬 디스패치, DB 기반 동적 잡 스케줄링을 구성했습니다. 모드별 실행 락으로 중복 진입을 막고 실패 재처리와 잔존 잡 정리를 적용했습니다.

다중 워커의 작업 분배

DB 작업 큐와 FOR UPDATE SKIP LOCKED 기반 작업 선점 구조를 개선했습니다. 트랜잭션 격리수준을 READ_COMMITTED로 조정하고 MariaDB → ClickHouse 적재를 증분 처리로 전환했습니다.

결과

로컬 모델 실행부터 분석 배치와 데이터 적재까지 연결하고, 운영 중 실패한 작업을 다시 처리할 수 있는 구조를 마련했습니다.

설계에서 고려한 점

구조화 출력은 응답 형식 제어에 사용했습니다. 형식이 맞는 응답도 분석 내용의 정확성을 보장하지 않으므로 응답 검증과 실패 처리 흐름을 함께 구성했습니다.

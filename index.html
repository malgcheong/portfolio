Reddit Translator 설계와 구현＋

문제

영문 게시글과 댓글을 매번 찾아 읽고 번역하는 과정을 줄이고, 읽은 자료를 다시 활용할 수 있는 개인 도구가 필요했습니다.

담당 역할

수집·번역·요약 엔진, 웹 UI, 데이터 저장, 다이제스트 편집 및 블로그 발행 흐름을 직접 설계·개발했습니다.

런타임의 역할 분리

웹·도메인 기능은 Spring Boot, 수집·LLM 처리는 FastAPI로 나누고 HTTP로 연결했습니다. 공유 DB에서도 수집 테이블과 요약 캐시의 관리 주체를 구분했습니다.

반복 호출과 실패 비용 줄이기

게시글 ID와 제공자별 요약 캐시를 적용했습니다. 댓글은 15개씩 번역하고, JSON 형식이 깨진 청크만 건별 번역으로 재처리합니다.

사람의 검토를 포함한 발행

다이제스트 편집·미리보기 후 발행하면 Astro 저장소에 Markdown을 작성하고 commit·push합니다. 이후 GitHub Actions가 블로그를 배포합니다.

결과

수집 → 번역 → 요약 → 편집 → 발행까지 연결해 개인적으로 사용하고 있습니다. 실제 발행 결과는 기술 블로그에서 확인할 수 있습니다.

설계에서 고려한 점

개인용 도구의 규모에 맞춰 수집 작업은 전역 락으로 직렬화했습니다. 자동 수집 스케줄러 대신 사용자가 수집을 요청하고 발행 전에 내용을 검토합니다.

reddit-orchestrator 설계와 구현＋

문제

Reddit Translator를 사용할 때마다 수집을 실행하고 다룰 글을 골라야 했습니다. 반복되는 작업은 자동으로 실행하되, 작성된 초안은 확인하고 승인할 수 있도록 만들고 싶었습니다.

담당 역할

LangGraph 실행 흐름과 로컬 모델 연동을 단독 개발했습니다. 초안 검사, PostgreSQL 체크포인트, Discord 승인 기능과 Spring Boot 실행 이력 대시보드도 구현했습니다.

LangGraph 실행 상태 관리

수집·선정·작성·검사·평가·승인·발행을 StateGraph의 7개 노드로 구성했습니다. OrchestratorState에 초안과 검사·승인 결과를 저장하고, 조건부 엣지로 다음 단계를 결정합니다. 각 단계의 모델, 토큰 수, 지연 시간도 함께 기록합니다.

API 연동에서 로컬 모델 운영으로

기존 도구에서는 DeepSeek 등 외부 API를 사용했습니다. Mac mini를 마련한 뒤에는 메모리에 맞는 모델을 고르고 Ollama 실행 환경을 구성했으며, MLX에서도 벤치마크를 진행했습니다. 글 선정에는 lfm2.5:8b, 초안 작성과 평가에는 qwen3.5:9b를 사용하고, 가벼운 분류 작업용으로 qwen3.5:4b를 구성했습니다. 워커 호출은 think=False로 설정했습니다.

초안 검사와 LLM 평가

선정한 글의 존재 여부, 중복, 길이, 금칙어를 코드로 검사하고 실패한 초안은 다음 단계로 보내지 않습니다. 통과한 초안은 qwen3.5:9b로 정확성·비중복·가독성을 평가합니다. 선정·평가 응답은 Ollama의 format 필드에 JSON Schema를 전달해 형식을 제한했습니다.

승인 대기와 실행 재개

PostgresSaver로 실행 상태를 저장하고, 승인 노드에서 interrupt()로 대기합니다. Discord 버튼이나 CLI로 승인·거절을 전달하면 Command(resume=...)로 재개합니다. 프로세스를 재시작해도 DB에 저장된 상태를 불러올 수 있습니다.

실행 이력 대시보드

Spring Boot 대시보드에서 PostgreSQL을 읽기 전용으로 조회합니다. 실행 목록과 단계별 처리 시간·토큰 수·평가 결과를 보여주고, 모델별 성공률과 평균 점수를 확인할 수 있도록 했습니다.

결과

M4 Mac mini 16GB에서 로컬 모델로 수집·선정·초안 작성·검사·평가를 실행했습니다. 승인 단계에서는 Discord로 미리보기를 보내고 응답을 기다립니다. 승인한 글은 블로그 저장소에 커밋하며, 원격 저장소로 push하는 옵션은 기본적으로 꺼 두었습니다.

설계에서 고려한 점

JSON 형식이 맞더라도 요약 내용은 틀릴 수 있습니다. 코드 검사와 LLM 평가를 통과한 글도 바로 발행하지 않고, 원문과 초안을 확인한 뒤 승인하도록 했습니다.

Java / Spring Batch / Ollama / MariaDB / ClickHouse

설계와 구현 자세히 보기＋

문제

수집 데이터의 키워드·감정·요약 분석을 배치로 처리하면서 모델 실행 환경, 응답 형식, 중복 실행과 실패 재처리를 함께 관리해야 했습니다.

담당 역할

stateless LLM 프록시 서버와 Spring Batch 분석 파이프라인을 단독 설계·개발했습니다. 수집 엔진의 분산 처리와 운영 안정화도 담당했습니다.

모델 호출과 배치 상태 분리

내부 GPU의 Ollama와 외부 AI API를 동적으로 분기하도록 구성했습니다. 분석 유형별 시스템 프롬프트 14종을 파일로 관리하고 Ollama 호출에 JSON Schema 기반 constrained decoding을 적용했습니다.

실행 환경에 맞춘 모델 구성

Gemma 4 26B(MoE), gpt-oss 120B 등 모델을 GPU 메모리 조건에 맞춰 선정하고 양자화·Modelfile·num_ctx를 조정했습니다.

반복 실행 가능한 배치

100건 단위 청크와 병렬 디스패치, DB 기반 동적 잡 스케줄링을 구성했습니다. 모드별 실행 락으로 중복 진입을 막고 실패 재처리와 잔존 잡 정리를 적용했습니다.

다중 워커의 작업 분배

DB 작업 큐와 FOR UPDATE SKIP LOCKED 기반 작업 선점 구조를 개선했습니다. 트랜잭션 격리수준을 READ_COMMITTED로 조정하고 MariaDB → ClickHouse 적재를 증분 처리로 전환했습니다.

운영 관제 — Zabbix (도구 비교·선택)

물리 11대·VM 14대와 서비스 상태를 Zabbix로 통합 감시하고 상태 대시보드와 연동했습니다. 폐쇄망·망분리 환경이라 Prometheus의 pull 방식(대상별 인바운드 개방)·단기 TSDB·쿠버네티스 동적확장이 맞지 않아, agent push로 인바운드를 최소화하고 MariaDB에 적재해 자체 화면과 연계할 수 있으며 네트워크 장비까지 관제되는 Zabbix를 선택했습니다.

CI/CD — 담당 서비스 배포 파이프라인

공통 코어를 GKE에 배포하는 팀 GitLab CI/CD(check·build·migrate·deploy·verify)에서 담당 서비스의 빌드·배포 잡과 DB 마이그레이션을 직접 작성·추가했습니다. Kaniko로 이미지를 빌드해 GCP Artifact Registry에 푸시하고, 팀이 구축한 GKE 블루그린 무중단 배포 구조 위에서 제 서비스가 배포되도록 연동했습니다.

결과

분석 요청, 배치 실행, 결과 적재를 구현했습니다. 실행 락과 실패 재처리를 추가해 중복 실행과 작업 실패에 대응했습니다.

설계에서 고려한 점

JSON Schema는 응답 형식을 제어하는 데 사용했습니다. 응답 완료 여부를 별도로 검증하고, 실패한 요청은 재처리하도록 구성했습니다.
